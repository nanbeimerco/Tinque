# UI調整 第3弾 実装計画書

作成日: 2026-10-21 / 対象: Tinque 2.3.7(`com.music.tinque`)

## 要望
1. ボトムバーのミニプレーヤーと歌詞画面の下のプレーヤーで、曲戻し・再生/停止・曲送りの**大きさの比率**を、メインプレーヤーに合わせる。
2. 検索しても**検索結果が表示されないことがある**。
3. **ロゴを各タブの左上**に置く。設定ボタンや戻るボタンのように画面に常駐させず、スクロールと一緒に流れるようにする。
4. **フォルダタブのガラスのカプセル**:曲が入ったフォルダ(アルバムアート表示の画面)では非表示にし、そこに至るまでの階層では表示する。
5. ライブラリタブの大見出し「ライブラリ」は必要か(→ 意見を5章に記載)。

## 2. 検索結果が表示されないことがある

### 原因(コードから特定)
[LocalSearchScreen.kt](../../app/src/main/java/com/music/bitchord/feature/localsearch/ui/LocalSearchScreen.kt) の検索処理は、次の順で動いている。

1. 入力から 0.14 秒待つ。
2. 裏側で検索する。
3. **結果一覧を先頭までスクロールする**(`listState.scrollToItem(0)`)。
4. 結果を画面に反映する。

3 の「スクロール」は、一覧が**一度も画面に表示されたことがない**と、一覧が表示されるまで待ち続ける。ところが一覧は「結果があるとき」にしか表示されないため、**3 で永久に止まり、4 に進まない**。画面は「結果なし」のまま変わらない。

これが起きるのは、例えば次のような場合で、「ときどき」起きる症状と一致する。

- 検索履歴が空の状態で、初めて検索したとき(履歴の一覧も表示されないため)。
- 検索タブに戻ってきたとき。入力した文字は復元されるが、一覧の表示状態は初期化されている。前回のタブ状態保持の変更で、こちらは起きやすくなっている。
- 直前の検索が「結果なし」で、一覧が一度も表示されていないとき。

### 対応
- 結果を**先に反映**し、スクロールは「待たない」方式(`requestScrollToItem(0)`)に変える。一覧がまだ表示されていなくても、表示された時点で先頭から始まる。
- 同じ待ち方をしているスクロール処理(フィルター切替時、入力を消したとき)も同様に直す。
- あわせて、**検索中は「結果なし」を出さない**。今は、入力直後の 0.14 秒と検索中にも「〜の結果はありません」が一瞬表示される。検索中は何も出さず(または小さなインジケーターを出し)、検索が終わってから「結果なし」を表示する。

## 3. ロゴを各タブの左上に(スクロールで流れる)

### 方針
- ロゴを、各タブの一覧の**先頭の項目**として置く。上部のボタン列と同じ高さ(52dp)の行の左端に表示する。
- 一覧の開始位置を、ステータスバーのすぐ下まで上げる。そうすると、**静止時の見た目は以前と同じ**(左上にロゴ、中央にページ名カプセル、右に設定ボタン)になり、スクロールするとロゴだけが一覧と一緒に上へ流れて消える。
  - 以前の帯は廃止したままにする。ロゴはガラスではないので、ルール0(固定の帯にガラスを置かない)とも矛盾しない。
- 共通部品 `TabLogoHeader` を1つ作り、各タブで使い回す。

### 対象と入れ方
| タブ | 入れ方 |
|---|---|
| 曲・アルバム・アーティスト・アルバムアーティスト([LocalMusicScreen.kt](../../app/src/main/java/com/music/bitchord/ui/screens/LocalMusicScreen.kt)) | 各タブの一覧(LazyColumn/Grid 計6か所のうち、トップ階層のもの)の先頭に追加 |
| フォルダ([FolderBrowserScreen.kt](../../app/src/main/java/com/music/bitchord/feature/localmusic/ui/FolderBrowserScreen.kt)) | フォルダ一覧の先頭(パンくずリストの上)に追加 |
| ライブラリ([LibraryHeaderBar.kt](../../app/src/main/java/com/music/bitchord/feature/library/ui/components/LibraryHeaderBar.kt)) | ヘッダーの先頭に追加(5章とセット) |
| 検索([LocalSearchScreen.kt](../../app/src/main/java/com/music/bitchord/feature/localsearch/ui/LocalSearchScreen.kt)) | 検索欄の上に置き、結果一覧をスクロールすると、ロゴの行だけが折りたたまれて隠れるようにする(検索欄とフィルターは上に残る) |

### 表示しない場所
- アルバムやフォルダを開いた先、プレイリストの中などの**下の階層**では出さない。戻るボタンがある画面は、左上が戻るボタンの場所になるため。
- 設定・Replay・EQ 画面には出さない(タブではないため)。

### 注意点
- 曲タブ等で「上部にタブ列を表示する」設定をオンにしている場合は、タブ列が一覧の上に固定される。その場合だけ、ロゴはタブ列の上(固定)に置く。

## 5. ライブラリの大見出し「ライブラリ」は必要か

### 意見: **不要。消して、他のタブと揃えるのがよい**

理由:
1. **他のタブとの統一**:曲・アルバム・フォルダ・検索には大見出しがなく、ガラスのカプセルでページ名を出している。大見出しがあるのはライブラリだけで、タブを切り替えたときにレイアウトが揃わない。
2. **ロゴとの重複**:3章でロゴが左上に入ると、「ロゴ → 大見出し → チップ」と見出しが2段重なり、最初の画面の上部が重くなる。
3. **情報の重複**:「ライブラリ」というページ名は、カプセルとボトムバーのタブ名で既に分かる。大見出しを消すと、その分だけお気に入りやプレイリストが上に来て、最初の画面に多く表示できる。
4. 大見出しが活きるのは、設定や Replay のように**タブから開く一段下のページ**(ボトムバーで場所が示されないページ)。こちらは今のまま残す。

### 変更後
- ライブラリの先頭は「ロゴの行 → フィルターのチップ列 → セクション」になる。
- カプセルは他のタブと同じく常に「ライブラリ」と表示する(スクロールを待たない)。

### 要確認
- H. 大見出しを消すか(推奨: 消す)。

## 6. 他タブ → アーティストタブで処理落ちする

### 原因(コードから特定)
曲・アルバム・アーティストの各タブは、[LocalMusicScreen.kt](../../app/src/main/java/com/music/bitchord/ui/screens/LocalMusicScreen.kt) という1つの画面を作り直して表示している。タブに入るたびに、次の重い処理を**メインスレッド(画面描画と同じスレッド)で、合成中に**実行していた。

1. **全曲の並べ替え**(`sortedSongs = songs.sortedForLibrary(...)`)。曲・アルバム・アーティストの全タブ共通。
2. **アーティストへのグループ分け**(`ArtistSplitter.groupSongsByArtist`)。アーティストタブのみ。全曲のアーティスト名を「feat.」や「&」で分割して名寄せし、さらに並べ替える。3つの処理の中で最も重い。
3. アーティストの画像(外部サービスから取得)の読み込み開始。最初に見える行の分。

タブを離れると画面が破棄されるため、毎回 1〜2 をやり直している。フォルダタブの処理落ち(前回修正)と同じ種類の問題。

### 対応
- フォルダのツリーと同じ方式で、**「並べ替え済みの曲」「アーティスト一覧」「アルバム一覧」を画面の外でキャッシュ**する。曲リスト・並び順・設定が同じなら再利用する。
- 作り直しが必要なときは**裏側のスレッドで計算**する。計算中は一覧の場所を空けたままにし、終わったら表示する(1回目だけ)。
- 計算結果の共有クラス `LibraryIndexCache` を1つ作り、曲・アルバム・アーティスト・アルバムアーティストの4タブで使う。
- 修正後に、`adb shell dumpsys gfxinfo` で切り替え時のカクつき(ジャンクフレーム)を修正前と比較する。

## 7. アーティスト → アルバムを選んだとき、遷移アニメーションがない

### 原因
アーティストを開いた先(アルバム一覧)も、そこから開いたアルバム画面も、画面切り替えの判定上は同じ「下の階層(drill)」という1つの状態になっている。状態の名前が変わらないので、アニメーション(横スライド)が起きず、中身が一瞬で入れ替わる。アルバム画面から戻るときも同じ。

### 対応
- 下の階層の深さを数える(アーティストのアルバム一覧 = 1、そこから開いたアルバム = 2)。
- 切り替えの判定に「深さ+開いている名前」を使い、深くなるときは右からスライドイン、浅くなるときは左へ戻るアニメーションにする。他の画面と同じ動き。
- アルバムアーティストタブ・ダウンロードの同じ遷移にも同じ修正が効く。

## 8. 曲・アルバム・アーティストタブを Material 3 デザインに統一するか(意見)

### 意見: **部分的に統一する。全部を同じグループコンテナにはしない。**

Material 3 Expressive のグループコンテナ(角丸の容器に数行をまとめる形)は、**項目数が限られた一覧**に向いている。例えば設定、フォルダ、ライブラリのセクションなど。一方、全曲一覧(数百〜数千曲)のような**長くて同じ種類の行が続く一覧**を1つの巨大な容器に入れると、次のデメリットがある。

- 角丸が画面の上下にしか見えず、グループに分ける意味がなくなる。
- 行ごとの切り抜き処理が数千行ぶん増え、スクロールが重くなりやすい(6章の処理落ちとも逆行する)。
- Apple Music や YouTube Music も、全曲一覧はフラットな行で表示している。

そこで、次の**共通ルール**で揃えることを提案する。

| 対象 | 方針 |
|---|---|
| **全タブ共通の部品** | 並べ替え・表示切替などの操作をライブラリと同じピル型チップに統一する。角丸・色(グレーのコンテナ色)・余白・文字サイズも揃える |
| **曲タブ** | 行はフラットのまま(今の区切り線をやめ、行間で区切る)。上部の件数・並べ替えの行だけ新しい部品に揃える |
| **アーティストタブ(リスト表示)** | **頭文字ごとのグループ**(A、B、C…/あ、か、さ…)に分け、各グループを Expressive コンテナにする。グループが区切りになり、目的のアーティストも探しやすい |
| **アルバムタブ(リスト表示)** | アーティストと同じく頭文字ごとのグループコンテナにする |
| **アルバム・アーティストのグリッド表示** | カードの角丸とコンテナ色だけを揃える(グリッドはカード自体がまとまりなので、容器には入れない) |

これで「短い一覧はグループ、長い一覧はフラット、操作部品と色・形は全タブ共通」という1つのルールになり、フォルダ・ライブラリとの見た目のズレがなくなる。

### 要確認
- I. 上記の部分統一でよいか(推奨: 部分統一。全曲一覧はフラット、アーティスト/アルバムのリストは頭文字グループ)。

## 9. グリッド表示の要素の大きさ(1画面の表示量)を調整できるようにする

### 現状
グリッド表示は5か所あり、要素の大きさはすべてコードに固定されている。

| 場所 | 今の指定 | スマホでの列数(目安) |
|---|---|---|
| 曲タブ | 最小幅 140dp | 2列 |
| アルバムタブ | 最小幅 140dp | 2列 |
| アーティストタブ | 最小幅 130dp | 2〜3列 |
| ライブラリ(プレイリスト) | 2列固定 | 2列 |
| アルバム/プレイリスト内の曲(グリッド表示) | 最小幅 140dp | 2列 |

### 対応
- 大きさは「**列数**」で指定する。最小幅で指定すると端末によって列数が変わり、結果が予想しにくいため。
  - 選べる列数: スマホでは 2〜5 列。タブレットや横向きでは、同じ大きさの要素が自動的に増える(列数を画面幅に比例させる)。
- 操作方法は2つ。
  1. **グリッド上で2本指でピンチ**:広げると要素が大きく(列が減る)、つまむと小さく(列が増える)。Google フォトと同じ操作。切り替わるときに軽い振動を出す。
  2. **設定 → 外観 →「グリッドの大きさ」**:タブごとにスライダーで列数を選ぶ。ピンチを知らない人向け。
- 設定は**タブごとに別々に保存**する(例: アルバムは3列、アーティストは4列)。
- 初期値は今と同じ見た目(2列、アーティストは3列)にする。
- 列数が増えると文字が窮屈になるので、4列以上では、アルバム名・アーティスト名の文字を1段小さくし、サブ情報(曲数など)を省略する。

### 要確認
- J. 操作方法(推奨: ピンチ+設定の両方)。

## 10. ミニプレーヤーのスワイプで曲送り/曲戻し(指に追従するプレビュー付き)

### 現状
- ミニプレーヤー全体を横にスワイプすると、指を離した時点で 72dp 以上動いていれば曲が変わる(左=曲送り、右=曲戻し)。
- ただし、**スワイプ中の見た目の変化がない**ため、スワイプで曲が変わることに気づきにくい。
- 曲戻しボタンを隠す設定はあるが、曲送りボタンは隠せない。

### 対応
1. **スワイプの対象をアルバムアートと曲名の部分に限定**する。ボタンの上から始まった操作は、ボタンの操作として扱う。
2. **指に追従するプレビュー**:
   - スワイプ中は、今の曲のアートと曲名が指と一緒に横へ動く。反対側から、**次の曲(左へスワイプ時)/前の曲(右へスワイプ時)のアートと曲名**が入ってくる。
   - 表示はアート+曲名の領域内に収め、外側(ボタン)には出さない。
   - 次/前の曲は、再生キュー(シャッフル時はシャッフル後の順番)から取る。キューの端で曲がない方向は、ゴムのように重く動いて元に戻る。
     - 前の曲がなくても、曲戻しで「今の曲の頭に戻る」ことはできる。その場合は今の曲のアートを左右に軽く揺らして、頭に戻したことを示す。
   - 指を離したとき、半分以上動いているか、勢いよく払った場合は、そのまま最後までスライドして曲を切り替える。それ以外はバネのように元に戻る。
   - 切り替え直後は、実際の再生曲が切り替わるまで入ってきた曲の表示を保ち、一瞬元の曲に戻るちらつきを防ぐ。
3. **ボタン表示のオプション**:今の「曲戻しボタンを表示」を、3択の「ミニプレーヤーのボタン」に置き換える。
   - すべて表示(曲戻し・再生/停止・曲送り)
   - 曲戻しを隠す(今の「オフ」と同じ)
   - **再生/停止のみ**(新規。曲の切り替えはスワイプで行う)
   - 今「曲戻しボタン」をオフにしている人は「曲戻しを隠す」に自動で移行する。
4. **再生/停止のみのときの位置**:曲送りボタンがあった位置、つまり**右端**に置く(右端の余白は今と同じ)。空いた分は曲名が使えるので、長い曲名も切れにくくなる。縮んだ状態のミニプレーヤーでも同じ配置にする。
- 対象: [MiniPlayerPull.kt](../../app/src/main/java/com/music/bitchord/ui/components/MiniPlayerPull.kt)(スワイプ処理)、[GlassNavBar.kt](../../app/src/main/java/com/music/bitchord/ui/components/GlassNavBar.kt)・[MiniPlayer.kt](../../app/src/main/java/com/music/bitchord/ui/components/MiniPlayer.kt)(表示)、`MainActivity`(前後の曲を渡す)、設定画面。

## 11. ボトムタブバーのピル:重なっている部分だけ色を変える

### 症状(ユーザー報告)
ピルの左右の端で一番外に出ている点から、縦にまっすぐ線を引いたとする。その線より内側にあるアイコン・文字が、すべて選択色に変わる。ピルは両端が丸いため、丸みの外側(ピルと重なっていない部分)まで色が変わって見える。

### 原因(コードで確認済み)
[FloatingTabBar.kt](../../app/src/main/java/com/music/bitchord/ui/components/floatingtabbar/FloatingTabBar.kt)(980〜1170行付近)では、アイコンと文字を次のように2回描いている(アートワーク連動テーマのとき)。

1. 通常色のコピー:ピルの範囲**外**だけ描く
2. 選択色のコピー:ピルの範囲**内**だけ描く

この「範囲」を作る切り抜き(`clipRect`)が、**ピルの左端〜右端の横幅だけを見た長方形**になっている。上下は要素の高さいっぱい(`top = 0`、`bottom = size.height`)。

```
  ピルの実際の形        今の切り抜き(長方形)
   ╭──────────╮          ┌──────────┐
  │            │         │          │
   ╰──────────╯          └──────────┘
   ↑ 角の外側も選択色になる
```

ピルは高さの半分を半径とする角丸(カプセル形)なので、両端の丸みの外側にある四隅も「範囲内」と判定され、選択色で描かれていた。ピルが横に動いていくと、この四隅の分だけ早く・広く色が変わるため、重なっていない部分の色が変わって見える。

同じ処理が、アイコン用・文字用、範囲内用・範囲外用の**計4か所にコピーされて**いる。

### 対応
1. **切り抜きをピルと同じカプセル形にする**:長方形の `clipRect` をやめ、ピルの実際の形(左右・上下の位置と、高さの半分の角丸)の `clipPath` で切り抜く。
   - 範囲内(選択色):カプセルの内側で切り抜く。
   - 範囲外(通常色):カプセルの外側で切り抜く(`ClipOp.Difference`)。
   - こうすると、内と外の境界がピルの輪郭とぴったり一致し、重なっている部分だけが色を変える。
2. **上下の位置も考慮する**:今の計算は横方向しか見ていない。カプセル形で切り抜くには、アイコン・文字がタブ列の中で縦のどこにあるかも必要になる。各要素のタブ列内での位置を取得し(`onPlaced` / `localPositionOf`)、ピルの上下の位置(タブ列の中央 ± 高さの半分)と合わせて計算する。
3. **ピルの変形にも追従する**:持ち上げ中は、ピルの幅・高さが伸び縮みする(`liveSize`:持ち上げで大きくなり、動きに合わせて横長/縦短に変形する)。切り抜きにも、実際に描かれているピルと同じ大きさ・変形を使う。
4. **4か所のコピーを1つの共通処理にまとめる**:アイコンと文字の両方で、同じ「カプセル形で塗り分ける」処理を使う。今後、片方だけ直し漏れることを防ぐため。

### 確認方法
- アートワーク連動テーマで、ピルを指で押さえたままゆっくり横に動かす。
  - アイコンと文字の色が、ピルの丸い輪郭に沿って切り替わることを確認する。
  - ピルの外側の四隅が通常色のままであることを確認する。
- 実機で「押さえたまま」を再現するため、`adb shell input swipe` を数秒かけて実行しながら画面を撮影し、修正前後を比較する。

### 補足
- アートワーク連動テーマ以外では、選択色と通常色が同じため、この問題は見た目に出ない(色の描き分け自体を行っていない)。
- ピルの周りの影(半径12dp)も外側にわずかに広がるが、これは「色が変わる」症状ではなく、ピルの下の影として意図されたもの。今回の症状の原因ではないため、変更しない。

## 12. ライブラリの「すべて表示」で、遷移先が左から入ってくる

### 原因(コードから特定)
[LibraryScreen.kt](../../app/src/main/java/com/music/bitchord/feature/library/ui/LibraryScreen.kt) の画面切り替えアニメーションは、行き先の名前だけで向きを決めている。

- 行き先が「プレイリスト/お気に入りの中(`drill:`)」→ 右からスライドイン(奥へ進む動き)
- **それ以外すべて** → 左からスライドイン(戻る動き)

「最近再生した曲」「よく再生する曲」の全件画面(`history:`)は「それ以外」に入るため、奥へ進む操作なのに**戻るときと同じ左からの動き**になっていた。逆に、そこから戻るときは「それ以外 → それ以外」で、やはり左から入る。

### 対応
- 7章と同じく、画面ごとに**深さ**を決め、深さの比較で向きを決める。
  - ライブラリのトップ = 0
  - 最近再生/よく再生の全件、お気に入り・プレイリストの中 = 1
- 深くなる(0→1)ときは右からスライドイン、浅くなる(1→0)ときは左へ戻る動きにする。同じ深さ同士の切り替え(フィルターのチップで「最近再生」→「よく再生」を直接切り替えた場合など)は、横スライドせずフェードにする。
- 7章(アーティスト→アルバム)と同じ仕組みを共通部品にして、ライブラリ・曲/アルバム/アーティスト・検索の各画面で使う。今後「戻るのに右から入る」のような食い違いが起きないようにするため。
